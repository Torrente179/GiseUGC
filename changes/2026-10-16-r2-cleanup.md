# R2 cleanup: superseded video copies deleted

**Status:** Done
**Date:** 2026-10-16

The user asked to delete from R2 the videos that are no longer worth keeping
now that the site plays higher-quality files. Nothing that plays changed.

## Deleted (5,904 files, 2.74 GB)

- `videos/hls/`: 5,807 files, 2.15 GB. These were the HLS ladders. Every
  site video plays its feed file (`videos/feed/v1`, see
  `changes/2026-10-14-feed-video-delivery.md`), and the player only reaches
  HLS for a clip without feed files. None of the 26 clips lacks them.
- `videos/mobile/` (30 files, 0.36 GB) and `videos/previews/` (30 files,
  0.05 GB): the old lower-quality mobile cuts and 480p preview loops. They
  were only the fallback if a feed file failed to load.
- `videos/starter/` (14 files): referenced nowhere.
- 23 `ugc-*` files at the bucket root: byte-for-byte duplicates of
  `videos/main/` and `videos/posters/`.

Earlier the same day: the Fiverr review videos' v1 (720p) and v2 (clean
original) copies, and the 7 videos taken off reviews.

## Kept (255 files, 7.43 GB)

- `videos/main/`: the masters. They also feed the Google video sitemap.
- `videos/feed/v1/`: what plays.
- `videos/posters/`.
- `videos/reviews/v3/`: the review videos, with Fiverr's mark.
- `images/reviews/v1/`: the client photos.

## Checks before deleting

- **Runtime data:** every video URL in the clip data and the services
  marquee resolves to feed files (`resolveFeedSource`).
- **Live pages:** none of the 48 sitemap pages embeds an old URL.
- **No orphans:** every file in `videos/feed/v1` belongs to a current
  rendition.

## Code

- **`AdaptiveVideo`:** if a feed file fails, it now falls back to the H.264
  feed file instead of the deleted preview/mobile copy.
- **Data:** the clip data still carries the old `mobileSrc`, `previewSrc`
  and `hlsSrc` URLs. They work as lookup keys that the feed resolver maps to
  the right file; nothing fetches them.
- **Tooling:** `scripts/encode-hls.sh` and `scripts/r2-upload-media.sh`
  would recreate the deleted folders if run. They aren't part of the current
  pipeline (`scripts/encode-feed.mjs`).

## Verified

On the live site, at 1440 and 390: the home, a service page and a vertical
load media only from `videos/feed`, `videos/reviews` and `images/reviews`,
with zero errors.

## Regression and fix (same day)

The cleanup broke the build's clip catalog, and the site silently lost all
16 newer clips (1001–1016).

- **What broke:** `scripts/generate-nuevos-r2-catalog.mjs` runs on every
  deploy (`prebuild` → `video:catalog`). It only kept a newer clip if its
  `mobile` and `preview` files answered 200 on R2. Those files were deleted
  here, so every deploy after the cleanup built an empty catalog. The 16 clips
  vanished from:
  - the portfolio;
  - the service and vertical pages (their "El trabajo" showed only the legacy
    clips);
  - the services marquee.

  Nothing 404'd, which is why the check after the cleanup (looking for errors
  on live pages) didn't catch it.
- **The fix:** readiness is now judged on what the site plays.
  - The generator checks the master, the poster, and the feed files
    `videos/feed/<v>/<slug>/avc.mp4` and `preview.avc.mp4`.
  - It no longer probes or emits HLS.
  - `mobileSrc`/`previewSrc` are still written, as the keys the feed resolver
    maps.
  - Locally: 16/16 ready.
- **Lesson:** after deleting media, compare the clip counts on live pages too,
  not only HTTP errors.
